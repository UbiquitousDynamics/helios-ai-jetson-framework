# Prompt for GPT Astra: build an automated end-to-end voice test suite

You are **GPT Astra**, working on the Helios AI repository. Build a reproducible, automated voice test suite that validates every live-conversation implementation task with real audio generated by the Piper voice already used by this project.

The suite must measure behavior end to end, not merely mock function calls:

```text
Piper-generated stimulus
        -> PC audio output
        -> Emilia/Helios microphone input
        -> Vosk / conversation controller / LLM / TTS
        -> Helios audio output
        -> PC microphone capture
        -> recorded response and machine-readable metrics
```

Do not claim that a test passes because a mocked callback fired. Use deterministic unit tests for logic and a separately labelled hardware-in-the-loop (HIL) layer for the acoustic path.

## Mandatory execution protocol

Work on exactly one test-suite task at a time. For each task:

1. Read only the files needed for that task and the current progress checkpoint.
2. Inspect existing Piper, Vosk, audio-device, diagnostic, KPI, and test infrastructure before adding code.
3. Implement the smallest independent test-harness increment.
4. Add deterministic fixtures and negative/failure-path tests.
5. Run focused tests, then the relevant existing regression tests.
6. Run the HIL test on the PC/Emilia target when the task requires hardware or acoustic evidence.
7. Repeat the complete validation gate until it passes, or mark the task blocked with evidence.
8. Update `docs/voice-test-suite-progress.md` with commands, versions, thresholds, raw sanitized metrics, and artifacts.
9. Stop and wait for the next execution turn. Never begin the next task automatically.

## Safety and test-isolation rules

- Use the existing Piper models and synthesis path. Do not create fake speech by writing arbitrary WAV samples when the test validates recognition.
- Generate the stimulus audio on the PC, play it through a selected PC output device, and capture Helios's response through a selected PC microphone/input device.
- Before HIL execution, require explicit device identifiers and a calibration step. Never silently use an unintended microphone or speaker.
- Prevent acoustic feedback: use headphones or isolated speakers, disable system monitoring/loopback, use a unique test marker, and abort on runaway level or repeated self-triggering.
- Never record real user speech. Use only generated fixtures and synthetic test phrases.
- Store audio and transcripts only in an explicit temporary artifact directory; sanitize or delete them according to a configurable retention policy.
- Do not place credentials, OAuth tokens, user audio, or raw sensitive transcripts in the repository or reports.
- HIL tests must have bounded duration, cleanup, process termination, and device-release behavior.
- Never change production thresholds solely to make a test pass. If an acoustic threshold is not calibrated, report `unverified` or `blocked`.
- Keep local deterministic tests separate from target-device HIL tests in reporting and CI markers.

## Required measurement model

Use a monotonic clock and a shared correlation ID for every stimulus/response exchange. Define timestamps for:

- `stimulus_synthesis_start` and `stimulus_ready`;
- `stimulus_playback_start` and `stimulus_playback_end`;
- microphone capture start/end;
- first provisional recognition;
- authoritative final recognition;
- model dispatch/start/first token/completion;
- first TTS synthesis and first Helios audio playback;
- first PC microphone response energy and response capture end;
- cancellation/interruption confirmation where applicable;
- task backend acknowledgement where applicable.

At minimum calculate:

- end-to-end latency: stimulus playback start → first valid Helios response audio;
- final-answer latency: stimulus playback start → response completion;
- STT latency: stimulus end → authoritative final transcript;
- model TTFB and generation duration;
- TTS first-audio latency and synthesis duration;
- interruption latency: user/stimulus speech onset → Helios audio stop/duck;
- endpointing latency and premature-finalization rate;
- recognition word error rate (WER), character error rate (CER), and exact-final rate;
- duplicate-dispatch rate and dropped/partial-only-turn rate;
- false barge-in and missed barge-in rates;
- response completeness and unexpected-overlap rate;
- task-state transition latency and verified-completion correctness;
- CPU, RAM, temperature, power, queue depth, and process/thread cleanup where available.

Every metric must have a definition, units, sample count, artifact source, and threshold. Use median, p95, maximum, and failure count where meaningful. Do not invent universal thresholds: put defaults in a versioned configuration file and require deployment calibration for Jetson-specific limits.

## Audio fixture requirements

Create a fixture catalog containing Italian and English cases, generated through the repository's configured Piper voices. Each fixture must declare:

- stable ID, language, text, expected authoritative transcript, expected intent, and privacy classification;
- whether it is a normal turn, pause/correction, barge-in, control command, task steering, noise case, or failure case;
- expected response constraints and applicable metric thresholds;
- whether it is safe for local-only or remote-enabled execution.

Generate deterministic audio with recorded synthesis metadata. Preserve the exact Piper model/version and sample rate in the artifact manifest. Include controlled silence, pauses, repetitions, self-corrections, overlapping speech, background noise, and TTS-echo fixtures without changing production code.

## Task-specific test coverage

Create a dedicated test group for each implementation task. Do not mark a task verified only because another task's tests pass.

### Test Task 00 — Baseline and requirement traceability

Verify the fixture catalog, metric definitions, hardware manifest, FR-01–FR-45 traceability, and reproducibility. No runtime behavior changes are allowed.

### Test Task 01 — Conversation events and floor states

Verify every legal and illegal transition, duplicate lifecycle event, concurrent snapshot, state recovery, and event correlation. HIL must confirm that observed playback/capture events map to the correct state without exposing raw speech in logs.

### Test Task 02 — Provisional versus authoritative transcripts

Play Piper-generated partial/revision fixtures. Verify that provisional text never dispatches to the model, tools, RAG, history, memory, or remote provider; exactly one authoritative final is dispatched; stale segments and duplicate finals are rejected.

### Test Task 03 — Adaptive turn endpointing

Measure short thinking pauses, long pauses, resumed speech, silence, noisy silence, explicit finals, maximum utterance bounds, and boundary timing. Report premature-finalization rate, late-finalization latency, missed-turn rate, and p95 endpointing latency.

### Test Task 04 — Intra-utterance self-correction

Use Italian and English fixtures such as “Tuesday... actually, Wednesday.” Verify final wording, one dispatch, no guessed semantic rewrite, exact-final rate, correction retention, and WER/CER.

### Test Task 05 — Realtime floor controller

Verify the complete event sequence from wake/activation through listening, finalization, thinking, speaking, and return to listening. Confirm one microphone owner, no duplicate capture stream, correct state under provider/TTS failure, and bounded recovery latency.

### Test Task 06 — Full-duplex capture

Play user fixtures while Helios is generating, synthesizing, starting playback, actively speaking, and draining playback. Verify capture continuity, bounded queue depth, no deadlock, no lost confirmed turn, and first-audio/end-to-end latency.

### Test Task 07 — Interruption and echo suppression

Use real Piper/TTS echo fixtures, genuine user-stimulus speech, low-energy noise, fuzzy echo, short hallucinated recognition, and repeated interruptions. Measure duck latency, confirmed interruption latency, false barge-in, missed barge-in, resume correctness, and residual echo rate.

### Test Task 08 — Local control intents

Verify offline `STOP_SPEAKING`, `MUTE`, `UNMUTE`, `SUSPEND_SESSION`, `RESUME_SESSION`, `END_SESSION`, and `CANCEL_TASK` in both languages. Confirm controls are never sent to the LLM, do not create ordinary conversation turns, and remain bounded under active playback.

### Test Task 09 — Wake and follow-up sessions

Verify wake-only activation, at least ten wake-free follow-ups, configurable expiry, explicit termination, reactivation, idle behavior, and reset. Measure activation latency, follow-up acceptance rate, false activation rate, and session-expiry correctness.

### Test Task 10 — Pacing and backchannels

Verify fast and slow model responses, delayed backchannel, supersession by real speech, interruption, dictation, controls, and sensitive confirmation. Measure backchannel delay, overlap duration, cancellation success, first-audio latency, and unnecessary-backchannel rate.

### Test Task 11 — Task-state core

Use the deterministic fake backend to verify all legal/illegal transitions for `PENDING`, `EXECUTING`, `WAITING_FOR_USER`, `COMPLETED`, `FAILED`, `CANCELLED`, and `SUPERSEDED`; cancellation races; bounded retention; and snapshot consistency.

### Test Task 12 — Task delegation and verified reporting

Verify conversation responsiveness during execution, progress notifications, confirmation gates, authoritative backend acknowledgement, failure/cancellation wording, and zero premature-success reports. Measure task latency and verified-completion precision/recall.

### Test Task 13 — Mid-task steering

Verify update, replacement, supersession, cancellation, repeated steering, late-result rejection, causal task IDs, and unaffected conversation history. Measure steering latency, stale-result rate, and supersession correctness.

### Test Task 14 — Privacy, fallback, and offline controls

Run privacy-denied, network-denied, provider-failure-before-speech, provider-failure-after-speech, local-only, and emergency-stop fixtures. Verify no unauthorized egress, no replay after speech commit, correct local fallback, and content-free metrics.

### Test Task 15 — Stress and shutdown

Run at least 50 generated turns, repeated barge-ins, task steering, queue pressure, cancellation at each pipeline phase, and bounded shutdown. Measure memory/thread/process growth, queue high-water marks, CPU/RAM/thermal behavior, cleanup time, and leaked-resource count.

### Test Task 16 — Final audit

Re-run the complete fixture catalog and full automated suite. Produce a requirement-to-test matrix for FR-01–FR-45, with separate local and HIL evidence, threshold configuration, skipped/blocked reasons, and reproducible commands.

## Threshold and pass/fail policy

- Store thresholds in a reviewed configuration file, never as hidden constants in tests.
- Include separate desktop and Jetson profiles.
- The default end-to-end first-audio threshold must be configurable; use a documented provisional value only until Emilia calibration is complete.
- A test passes only if all mandatory assertions and metric thresholds pass for the declared sample count.
- A p95 failure, false-interruption rate above threshold, unauthorized egress, duplicate authoritative dispatch, leaked worker, or unverified task completion is a hard failure.
- If the device is unavailable, mark HIL `blocked` rather than converting it into a local pass.
- Do not average away outliers; retain raw per-case timing locally and publish sanitized aggregates.

## Required artifacts

For each test task, create only the necessary artifacts:

- versioned fixture manifest;
- threshold profile and environment manifest;
- sanitized JSON/JSONL results with correlation IDs;
- optional audio paths under an ignored temporary directory;
- concise Markdown report linked from `docs/voice-test-suite-progress.md`.

The report must state: task ID, implementation under test, exact commands, Python/dependency/device versions, fixture count, pass/fail/blocked counts, metric summaries (median/p95/max), threshold profile, failures with causes, cleanup result, and next task. Never include passwords, tokens, raw user data, or credentials.
